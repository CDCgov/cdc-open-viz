# Project Overview

This document is a high-level contributor guide for the CDC Open Visualization Environment
(COVE) repository. It summarizes what the project does, how the monorepo is organized, and
which commands and docs to use before making changes.

## 1. Project Purpose

COVE is a Yarn workspaces and Lerna monorepo for React-based CDC visualization packages.
It builds reusable components for charts, maps, dashboards, data tables, data callouts,
markup includes, and related authoring and embed workflows.

The main maintainers and contributors are developers working on CDC visualization packages,
shared editor/runtime infrastructure, Storybook previews, configuration contracts, and
partner embed support. External consumers include React apps, CDC WCMS integrations, and
partner sites that render published visualizations from saved configs or embed URLs.

Important project concepts:

- `config` and `configUrl`: Most visualization packages render from a saved configuration
  object or fetch one from a URL.
- Authoring vs runtime: `@cdc/editor` helps create configs; the visualization packages
  render those configs.
- Shared shell: packages use shared COVE wrapper/layout/styling primitives from
  `@cdc/core`.
- Dashboards: `@cdc/dashboard` composes multiple visualization configs into rows, columns,
  widgets, shared filters, and optional multi-dashboard tabs.
- Migrations: saved configs are migrated through shared versioned helpers in
  `packages/core/helpers/ver` via `packages/core/helpers/coveUpdateWorker.ts`.
- Storybook play tests: many user-facing/editor interactions are verified through stories
  under `_stories` and package `_stories` folders.

## 2. Repository Structure

Core repo areas:

| Path | Purpose |
| --- | --- |
| `packages/` | Workspace packages published or consumed as `@cdc/*` packages. |
| `packages/core/` | Foundation package with shared components, styles, helpers, hooks, assets, types, testing helpers, and migrations. |
| `packages/chart/` | Chart renderer for bar, line, pie, combo, radar, Sankey, forest plot, heatmap, and related chart families. |
| `packages/map/` | US/world map renderer with geographic data, legends, tooltips, bubbles, patterns, and map-specific helpers. |
| `packages/dashboard/` | Orchestrator for composing visualizations into dashboards with shared filters and layouts. |
| `packages/editor/` | Authoring UI for creating and editing visualization configs. |
| `packages/embed/` | Partner embed page/helper system for iframe-based external embeds. |
| `packages/data-bite/` | Highlighted metric/card-style component. |
| `packages/data-table/` | Standalone tabular data component. |
| `packages/markup-include/` | Component for authored inline or remote HTML content. |
| `packages/waffle-chart/` | Waffle-style highlighted metric component. |
| `packages/filtered-text/` | Deprecated legacy filtered-text component kept for existing saved configs. |
| `.storybook/` | Root Storybook configuration, themes, preview setup, and static assets. |
| `_stories/` | Root-level guide and comparison stories. |
| `dev-portal/` | Local multi-package development portal and compare-mode Vite config. |
| `docs/` | Contributor context docs for testing, migrations, package dependencies, config docs, and feature-specific behavior. |
| `scripts/` | Repo utility scripts such as package usage CSV export. |
| `patches/` | `patch-package` patches applied after install. |
| `.vscode/` | Discoverable tasks and MCP server definitions for Storybook and Playwright. |
| `.agents/` and `_bmad/` | AI/BMad workflow support files for this repo. |

The monorepo is managed by root `package.json` workspaces (`packages/*`) and `lerna.json`
with independent package versions.

Internal dependency rules are documented in `docs/PACKAGE_DEPENDENCIES.md`:

- `@cdc/core` is the foundation and must not depend on other internal packages.
- Standalone visualization packages may depend on `@cdc/core`, but should not depend on
  sibling visualization packages.
- `@cdc/dashboard` and `@cdc/editor` are orchestrators and may depend on the full workspace.
- Story files are exempt from these dependency restrictions.
- Type-only imports across package boundaries are still architectural violations; move
  shared types to `@cdc/core` instead.

## 3. Core Libraries And Tooling

Primary tooling:

- Package manager: Yarn Classic, used through root `yarn ...` scripts.
- Monorepo runner: Lerna 8 with Yarn workspaces.
- Runtime framework: React 18 and React DOM 18.
- Build tool: Vite 7 with shared package config generated by
  `packages/core/generateViteConfig.js`.
- Storybook: Storybook 10 with `@storybook/react-vite`, docs, a11y, Vitest, and MCP addons.
- Tests: Vitest 3, Testing Library, Storybook play-function tests, and Playwright-backed
  browser tests for the Storybook Vitest project.
- Styling: Sass, package CSS/SCSS, compiled shared core CSS, Bootstrap 4.6 expectations for
  host integrations, and `stylelint`.
- Formatting/linting: Prettier, ESLint, `@typescript-eslint`, React Hooks ESLint rules, and
  `lint-staged`.

Important libraries used by packages include `@visx/*`, `d3`, `d3-geo`, `topojson-client`,
`chroma-js`, `papaparse`, `dompurify`, `html-react-parser`, `react-accessible-accordion`,
`react-dnd`, `react-select`, `react-tooltip`, `vega`, and `vega-lite`.

Repo-specific helpers and utilities to know:

- `@cdc/core/helpers/testing` contains shared Storybook/editor interaction test helpers.
- `packages/core/generateViteConfig.js` centralizes package Vite config, SVG support,
  CSV/DSV loading, CSS injection, package dev templates, and the `/__examples` dev endpoint.
- `packages/core/helpers/coveUpdateWorker.ts` is the shared config migration pipeline.
- `packages/core/CONFIG.md` documents shared configuration structures reused across packages.
- Package-level `CONFIG.md` files document package-owned authorable config fields.

## 4. Local Development Workflow

Install dependencies from the repo root:

```bash
yarn install
```

Build all packages in dependency order:

```bash
yarn build
```

Start the shared Storybook instance on port `6006`:

```bash
yarn storybook
```

Run the local multi-package dev portal on port `8080`:

```bash
yarn dev:portal
```

Run the compare-mode portal:

```bash
yarn dev:compare
```

Run a single package locally:

```bash
yarn dev:chart
yarn dev:dashboard
yarn dev:data-bite
yarn dev:data-table
yarn dev:editor
yarn dev:filtered-text
yarn dev:map
yarn dev:markup-include
yarn dev:waffle-chart
```

Default package dev ports from root scripts:

| Package script | Port |
| --- | --- |
| `yarn dev:chart` | `3001` |
| `yarn dev:dashboard` | `3003` |
| `yarn dev:data-bite` | `3004` |
| `yarn dev:data-table` | `3005` |
| `yarn dev:editor` | `3006` |
| `yarn dev:filtered-text` | `3007` |
| `yarn dev:map` | `3008` |
| `yarn dev:markup-include` | `3009` |
| `yarn dev:waffle-chart` | `3010` |

Environment assumptions:

- The repo does not currently pin Node in `.nvmrc` or `.node-version`; use a Node version
  compatible with Vite 7, Storybook 10, and the checked-in Yarn workflow.
- Use root `yarn ...` scripts rather than globally installed `lerna`.
- `patch-package` runs on `postinstall` and applies patches from `patches/`.
- Host apps that integrate packages should include Bootstrap 4.6 CSS and, when needed,
  the compiled shared stylesheet from `@cdc/core/dist/cove-main.css`.

## 5. Testing Strategy

Follow the repo guidance in `AGENTS.md`: default to targeted tests for the files or
components changed; use quick suites for broad changes; do not run full suites unless the
user explicitly asks for them.

Targeted unit test command shape:

```bash
yarn test-unit:quick -- --scope @cdc/<package-name> -- src/.../<file>.test.<js|jsx|ts|tsx>
```

Example:

```bash
yarn test-unit:quick -- --scope @cdc/dashboard -- src/test/CdcDashboardComponent.test.tsx
```

Targeted Storybook test command shape:

```bash
yarn test-storybook:quick packages/.../_stories/<file>.stories.<js|jsx|ts|tsx>
```

Example:

```bash
yarn test-storybook:quick packages/chart/src/_stories/ChartEditor.stories.tsx
```

Quick suites:

```bash
yarn test-unit:quick
yarn test-storybook:quick
```

Full suites, opt-in only:

```bash
yarn test-unit
yarn test-storybook
```

Other validation commands:

```bash
yarn lint
yarn lint:css
yarn sync:check
yarn knip
```

Test locations:

- Unit tests: `packages/**/src/**/*.{test,spec}.{js,ts,jsx,tsx}` plus package `tests`,
  `components`, and `helpers` test files included by `vitest.config.ts`.
- Story tests: `_stories/**/*.stories.@(js|jsx|ts|tsx)` and
  `packages/**/_stories/*.stories.@(js|jsx|ts|tsx)`.
- MDX Storybook docs: `_stories/**/*.stories.mdx` and package `_stories/**/*.stories.mdx`;
  these are usually docs-only.
- Quick Storybook mode sets `COVE_QUICK_TESTS=1` and excludes
  `*.smoke.stories.@(js|jsx|ts|tsx)`.
- Shared test wiring lives in `vitest.config.ts` and `vitest.setup.ts`.

Story/editor test conventions from `docs/TESTING_BEST_PRACTICES.md`:

- Use shared helpers from `@cdc/core/helpers/testing`, especially `performAndAssert`,
  `waitForEditor`, `openAccordion`, and `assertVisualizationRendered`.
- Assert on the visualization output, not only editor control state.
- Prefer specific visual changes over generic DOM or HTML changes.
- Do not add ad-hoc sleeps or polling when a shared helper exists.
- Keep editor Storybook tests focused, often one accordion section per test story.

VS Code task shortcuts are defined in `.vscode/tasks.json`, including Storybook start,
targeted Storybook tests, quick/full Storybook tests, and quick/full unit tests.

The Storybook MCP server is available at `http://localhost:6006/mcp` only while Storybook is
running. The optional Playwright MCP server is configured in `.vscode/mcp.json`.

## 6. Branching And Review Workflow

Feature branches usually branch from `dev`; compare feature work against `dev` by default.
This is documented in `AGENTS.md`.

For reviews and change summaries:

- Use `dev...HEAD` as the default comparison range unless the user specifies another base.
- Keep changes scoped to the affected package, shared helper, or doc.
- Respect the dependency tiers in `docs/PACKAGE_DEPENDENCIES.md`.
- Add or update targeted tests for changed behavior.
- Update relevant docs in the same change when config, migrations, or documented behavior
  changes.

Versioning and release notes visible in the repo:

- Lerna is configured with independent versions in `lerna.json`.
- Package manifests currently use `4.x` package versions.
- Migration versions follow the COVE release-style version format, including suffixed
  follow-up versions such as `4.26.4-1`.
- The root `publish` script delegates to `npx lerna publish`; do not publish unless that is
  explicitly part of the task.

## 7. Configuration And Migrations

Consumer-facing config documentation lives in package `CONFIG.md` files:

- Shared reusable structures: `packages/core/CONFIG.md`.
- Package-owned fields: `packages/<package>/CONFIG.md`.
- Config doc maintenance rules: `docs/CONFIG_DOCUMENTATION_GUIDE.md`.

Review config docs when changing:

- authorable config fields,
- package defaults or initial state,
- supported enum values,
- migrations or legacy-config handling,
- editor-exported config fields consumers may encounter,
- runtime behavior that changes how a documented field is interpreted.

Minimum example conventions:

- Documented packages should have `packages/<package>/examples/minimal-example.json`.
- README examples are intended to stay in sync with those minimal examples.
- Do not update minimal examples unless the true minimum working config changes or the
  current example no longer renders.

Migration code lives in:

- `packages/core/helpers/coveUpdateWorker.ts`
- `packages/core/helpers/ver/*.ts`
- migration tests under `packages/core/helpers/ver/tests/`

Before editing migrations, read `docs/MIGRATION_SYSTEM.md`. Key rules:

- Do not guess whether to update an existing migration or add a new one; ask the user.
- Add new migration files under `packages/core/helpers/ver`.
- Import and place new migrations in `packages/core/helpers/coveUpdateWorker.ts` in version
  order.
- Suffixed migrations should be inserted immediately after their base version.
- Add targeted migration tests for the behavior changed.
- In migration tests, assert on the fields changed by the migration, not only on the final
  `result.version`.

## 8. Contributor Conventions

Read the relevant context document before working in a specialized area:

| Document | Use When |
| --- | --- |
| `docs/TESTING_BEST_PRACTICES.md` | Writing or reviewing editor interaction tests. |
| `docs/CONFIG_DOCUMENTATION_GUIDE.md` | Maintaining package `CONFIG.md` files. |
| `docs/PACKAGE_DEPENDENCIES.md` | Adding internal package imports or moving shared code. |
| `docs/MIGRATION_SYSTEM.md` | Editing shared config migrations or migration ordering. |
| `docs/FILTERED_TEXT_DEPRECATION.md` | Working on filtered-text deprecation behavior. |
| `docs/DASHBOARD_CONDITIONS.md` | Working on dashboard condition visibility logic. |
| `docs/DASHBOARD_FILTERS_FLOW.md` | Working on dashboard filters or filter data flow. |
| `docs/PALETTE_MIGRATION.md` | Working on palette migration or palette selection. |
| `docs/CHART_Y_AXIS_DOMAIN.md` | Working on chart Y-axis domain behavior. |
| `docs/COVE_EVENTS.md` | Adding analytics events or metrics behavior. |
| `docs/VISUALIZATION_WRAPPERS.md` | Working on visualization wrappers or shell consistency. |
| `docs/BUTTON_SYSTEM.md` | Working on shared buttons or legacy `.btn` migration. |

Coding and formatting conventions:

- Prefer existing package patterns and shared helpers over new abstractions.
- Use `@cdc/core` for genuinely shared helpers, types, and components.
- Avoid cross-package imports from standalone visualization packages into sibling packages.
- Keep package-owned config docs in that package, even when the TypeScript type lives in
  `@cdc/core`.
- Use Prettier settings from `.prettierrc`: no semicolons, single quotes, print width 120.
- ESLint disallows `console` except `console.error` and `console.warn`, and disallows
  `debugger`.
- Stylelint enforces alphabetical CSS properties.
- For Storybook/editor tests, use the shared testing helpers rather than local polling.
- Do not run full test suites unless requested.

Documentation expectations:

- Update package `CONFIG.md` when consumer-facing config changes.
- Update or add focused docs under `docs/` when a substantial feature has non-obvious data
  flow, state management, conventions, gotchas, or multi-package interactions.
- Keep docs concrete: prefer exact commands, package paths, and source-of-truth files.

Before making changes:

- Identify the package or shared area that owns the behavior.
- Read the matching context doc from `docs/` when one exists.
- Check dependency boundaries before adding imports.
- Check whether the change affects consumer-facing config or migrations.
- Find the closest unit or Storybook test and run the targeted command.
- Prefer quick suites only when the change spans broad behavior.
- Avoid full suites unless explicitly requested.
- Review the diff for unrelated churn before handing off or opening a PR.
